User explicitly objected to hand-rolled HTTP parsing in birdburner ('esp http 没有框架？你别造轮子'). Future HTTP work should use an existing framework — ESP-IDF esp_http_server or Rust esp-idf-svc (requires ESP-IDF runtime migration) or a suitable no_std crate — keeping only app-level JSON validation and PID/sensor logic custom. Do not extend the manual HTTP/TCP parser in `src/http_api.rs`/`src/main.rs`.

Current API endpoints (as implemented there): GET `/api/status`; POST `/api/target` with JSON `{ "target_c": 23.5 }` (15–30 °C in 0.5 °C steps, RAM-only, default 25 °C); empty-body POST `/api/stop`. Target updates only store/display; PID disabled; stop latches a five-second test-stopped state until reboot; no auth/TLS (trusted LAN only).

Host tests share firmware via `tests/host/lib.rs`; `.cargo/config.toml` defaults to the embedded target, so run `cargo test --manifest-path tests/host/Cargo.toml --target x86_64-unknown-linux-gnu --target-dir target/host-tests`. TCP smoke: build `api-smoke-server` with same manifest/target/target-dir, run `python3 tools/api_smoke.py` (loopback/simulated, not physical GPIO). Embedded binaries: `cargo build --release --bins`. Docs/curl examples in `README.md`.
