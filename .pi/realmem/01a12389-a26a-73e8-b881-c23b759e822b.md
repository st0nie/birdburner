`src/heater_control.rs` implements direction-aware conditional integration (clamping), not back-calculation. With `error = target - actual`, compute `step = Ki * error * dt`, bound candidate I to `0..output_limit_pct`, and form candidate `P + I + D`. Freeze only when candidate output exceeds the upper cap and step is positive, or is below zero and step is negative. Permit steps towards the realizable output range even while P or D keeps the candidate saturated. Preserve holding power at the setpoint; do not unconditionally decay I or clear it upon crossing the target. The existing target+1 °C forced-off guard, derivative filter, gains, PWM and sensor safety policies are independent and unchanged.

Five `conditional_integration_*` tests in the same file exercise outward freeze at both limits, corrective updates while still saturated because of D, return to unsaturated control, exact bounds and the integral's own limits. Run them with `cargo test --manifest-path tests/host/Cargo.toml --locked --target x86_64-unknown-linux-gnu --target-dir target/host-tests conditional_integration_`.

A valid clamping example is target25 °C, measurement25.3 °C, Kp20, I4%, D0: requested output is -2%, executed output0%, and negative-error integration freezes. Nonzero I at zero output is therefore not itself a bug or proof of ongoing heating. Prometheus heater duty/on-time represent GPIO commands, not measured load power. Zero-command high-temperature periods require an independent assessment of thermal conditions or actual load current; this anti-windup correction cannot actively cool.

Primary references: MathWorks https://www.mathworks.com/help/simulink/slref/pidcontroller.html (Anti-windup method) and Beckhoff https://infosys.beckhoff.com/content/1033/tf8000_tc3_hvac/4685059723.html (Anti-Reset-Windup).
